# SUPERPOWERS: 단계별 agent 유지 (작은 변경)

## 의도
지금은 현재 단계 밑에만 agent가 최대 4줄 보이고, 단계가 넘어가면 이전 단계 작업이 사라지거나 현재 단계 밑에 섞여 보인다. 각 단계가 끝난 뒤에도 그 단계에서 돈 agent가 그 단계 밑에 남아, 어느 단계가 무엇을 했는지 보이게 한다.

## 동작
- role이 있는 agent(impl / review)는 자기가 시작된 단계 밑에 보인다. 끝난 단계, 현재 단계 모두 같다.
- 단계마다 agent 행은 최대 5줄이고, 넘치면 `… N more` 한 줄이 더 붙는다.
- 정렬: 실행 중 → 문제 있었던 것(`⚠` issues, `✗` failed) → 최신(n 내림차순).
  - 끝난 단계에서 문제를 먼저 보여주는 건 사용자가 정한 것이다.
  - 현재 단계에도 같은 순서를 쓰는 건 내 결정이다. 규칙을 하나로 두려고 그렇게 했다.
- agent가 없는 단계(spec, plan 등)는 지금처럼 한 줄만 나온다. execute의 plan 막대와 현재 task 줄은 그대로 두고, agent 행은 그 아래에 붙는다.

```
✓ execute ██████████ 10/10            02:59
  │ ✓ impl #10           Opus 5.5     00:13
  │ ⚠ review #3          issues       00:09
  │ ...
  │   … 15 more
✓ review                              00:12
  │ ✓ review whole branch  approved   00:10
● finish
```

## 접근 방식
1. **시각으로 단계 판정 (선택)**: `sp.at`의 단계 시작 시각과 agent의 `startedAt`을 비교해서, `startedAt` 이전에 시작한 단계 중 가장 늦은 단계에 넣는다. 저장하는 상태가 바뀌지 않고 기존 세션에도 바로 맞는다. 경계 시각에서는 판정이 추정이 된다.
2. **dispatch 시 stage 저장**: `AgentRun.stage`를 추가한다. 판정이 명시적이지만, 타입·등록 로직·기존 데이터 처리를 모두 고쳐야 한다.

1번을 골랐다. 바꾸는 범위가 가장 작고 기존 데이터에도 맞기 때문이다.

## 제약 / 비목표
- 저장 형식(`types`)과 등록 로직은 건드리지 않는다.
  - 예외는 `MAX_AGENTS`를 20에서 50으로 올리는 것이다(내 결정). 10-task 사이클이면 agent가 22개라, 20개 상한에서는 앞 단계 agent가 지워진다.
- 이전 사이클의 agent는 현재 사이클 첫 단계보다 먼저 시작했으므로 어느 단계에도 속하지 않아 숨겨진다(내 결정).
- finish에서는 지금처럼 role이 붙지 않으므로 finish 밑에는 agent가 없다.

## 구현자에게 남김
- 단계 판정 함수는 `superpowers.ts`에 두고 `superpowers.test.ts`에 테스트 하나를 추가한다.
- 판정은 `startedAt >= at[stage]`인 단계 중 `at`이 가장 큰 단계로 한다.
